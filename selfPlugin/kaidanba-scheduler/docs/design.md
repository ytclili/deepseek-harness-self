# 定时商品推送设计

用户已确认当前页面与独立 JSON 存储方案，正式版本实现持久化调度，不再保存临时草稿。

配置入口复用 Harness `settings.section`，名称「定时商品推送」，顺序 22。白灰底色与 IM 相同蓝色主按钮；单次和每日任务都使用北京时间。描述仅作备注；任务固定推送商品，不让模型解释任意代码或 SQL。

页面通过宿主认证连接访问 `/api/kaidanba-scheduler`。后端使用 `connection.fetch.register` 接入原有 Host/Origin 和登录校验，不开额外 HTTP 服务。保存采用 revision 冲突检查；失败保留表单。客户端读取 IM 已保存目标和已聊会话，只有用户保存时才将所选会话注册为投递目标。

调度器每秒扫描到期任务，先将执行快照、 occurrence 和下一执行时间原子落盘，再查询商品。通过根工具服务执行 `goods_list`，不复制业务接口调用。发送前检查任务仍有效，落盘 `sending` 后调用 `dshIm.send`。平台、机器人和目标在执行时重新验证。查询与发送均有超时和取消信号，同任务不重叠执行。

发送仅包含商品名称、规格、单位、价格；不自行添加币种，不包含库存、内部 ID 或原始响应。列表不完整或文字过长明确失败。工具当前最多返回 100 条，不翻页。

执行状态：准备中、查询失败、发送中、平台已接受、明确发送失败、结果待确认、已错过、已取消。外部 IM 没有幂等接口，不能承诺恰好一次。模糊发送失败不自动重发；用户应先核对消息。暂停或删除阻止尚未发送的执行，不能撤回已发消息。

单次任务消费时点后结束，每日任务计算未来下一个北京时间。超过一分钟的到期任务记为错过；重启时所有过去时点记为错过，不补发。启动恢复中的发送记为待确认，准备阶段取消。离线备份恢复工具将所有未结束任务暂停。

第一版为单 profile 单实例，使用同一企业工具业务账户；没有多租户数据授权、飞书卡片或微信平台限制绕过。相关存储结构见 data-impact.md，部署及恢复步骤见 README.md。
